# School security policy

School Admins manage their own school in **Settings → School security policy**. Super Admin MFA is mandatory for access to the platform console and any school workspace under that identity. School Admins control school roles only.

## Implementation and verification checklist

“Local API” means the Express routes and real PostgreSQL migrations were exercised in a disposable database with provider sessions and factors represented by test fixtures. “Browser” means desktop and mobile Playwright with mocked API/provider responses. Hosted Supabase settings, real TOTP devices, and external email delivery require staging verification.

## Security event coverage

- **Sign-ins and sessions:** Vidyalayaa records a successful session once it is used through its API. Supabase login and sign-out entries can supplement this log. Provider sign-in or verification attempts with no confirmed outcome are shown as **Attempted**.
- **Failed sign-ins:** Supabase Auth can reject a password, MFA or OAuth request before Vidyalayaa receives a session. A rejected attempt that cannot be tied to an identified school account cannot safely appear in a school’s audit log. Use the project’s Supabase Auth logs for these failures. Custom password-attempt tracking requires the provider hook.
- **MFA and passwords:** Enrollment attempts, factor removal, verification and password changes appear when the provider emits matching events and **Authentication → Audit Logs → Write audit logs to the database** is enabled. Verified email changes also have a Vidyalayaa event. Device and IP fields can be unavailable for provider events.
- **Tenant privacy:** Provider and account-wide events appear only for identities exclusively associated with the school, excluding platform staff. School-specific membership actions remain visible even for a shared account. The School Admin feed is limited to 90 days. Credentials, raw provider payloads and raw user-agent strings are never returned.
- **Project-wide permissions:** Role changes are captured when a school membership changes. Application permission definitions and Supabase project permissions are controlled by deployment and the provider, outside the School Admin editor.

## Rollout and recovery

1. Apply the repository migration through the existing migration runner with `npm run db:migrate` and verify with `npm run db:verify`. Deploy the API, worker, and frontend afterward. The migration preserves existing school policies and provider sessions.
2. For password security, use the Supabase Auth project dashboard or set `AUTH_PASSWORD_MIN_LENGTH` in the private `.env.auth`. Run `npm run auth:configure` to preview. Review the project-wide changes before `npm run auth:configure -- --apply`. The existing tool verifies the provider settings by reading them back.
3. Before increasing MFA, have two independently controlled School Admin accounts enroll a TOTP authenticator. Verify the backup administrator can sign in from a separate browser. Record the approval and recovery procedure without secrets. A backup administrator can sign in with their own MFA and restore the previous settings as a new approved version if necessary. Recovery for a lost factor must follow verified account recovery with an authorized Supabase operator.
4. Verify the policy in a staging school with a test account for each affected role. Use a genuine Supabase sign-in, TOTP challenge, and delivery address. Check sign-in after disabling and re-enabling a role, then suspend a test account and verify that a previously issued session is rejected. Check worker logs and the verified inbox when testing security alerts.
