# Class-wise School Admin results

Open **Results** (`/admin/r/marks`), choose a **Class and section**, and then an **Examination** from that section. Each class row is the existing section/session record; sections with the same grade remain separate. Choices include academic-session labels and load every page of classes and examinations.

After choosing an examination, its student marks appear. **Add record** asks for a student enrolled in that section. For a subject test, the subject is fixed to the test's subject. For an official examination, choose a subject configured for the section through its existing teacher-subject assignments. The dialog shows the selected class, examination and maximum score. Changing class clears the examination and removes the previous results/form context.

**Import CSV** uses the examination already selected on Results. The examination is fixed in the import dialog. Student and subject codes are resolved against the examination's class, and the existing bulk endpoint validates the complete upload before saving. Only OPEN examinations offer entry, editing and CSV upload; DRAFT, LOCKED and PUBLISHED examinations remain available for viewing. Manage examinations preserves the existing examination workflow; creating a subject test now filters its subject choices by class and clears the subject when the class changes.

## Filled CSV and roll-number entry

School Admin selects a class/section and open examination on Results. Teachers choose their assigned class under Subject Tests or their Class Teacher class under Official Results. Both have these options:

1. **Import CSV / Upload marks CSV → Download filled CSV template**: select a configured subject. The download includes the examination ID/name, class, section, roll number, student code/name, subject code/name, score and remarks. Existing scores and remarks are prefilled. Enter scores and upload the same CSV. Keep identifying columns unchanged and preserve codes/roll numbers as Text in spreadsheet software. Blank scores are skipped, never converted to zero or used to delete marks. Enter `0` explicitly when zero is intended. Legacy `student_code,subject_code,score,remarks` files remain supported. For classes over 500 students, select a separate 500-row batch; all students are available across batches.
2. **Enter by roll number**: choose a subject and start with the first enrolled student. The roster uses numeric-aware ordering (1, 2, 10), with student code as the fallback for missing rolls. Type a score and press Enter, or select **Save & next student**. A valid score is queued immediately and the next student's input opens and receives focus without waiting for the server. Existing scores are shown for review. **Skip student** leaves records unchanged, and the selector allows jumping directly to a roll number. Invalid scores stay on the current student. An ordered background queue saves one entry at a time and reports confirmed versus pending saves; confirmations do not reset the score currently being typed. Repeated edits to the same record keep their submission order. Holding Enter does not repeatedly submit prefilled marks.

If a background save fails or its response is lost, the queue pauses, retains every unconfirmed score and shows **Retry pending saves**. Retries preserve each request's original idempotency key. Wait for **All entered marks saved** before leaving. Closing with unconfirmed entries requires confirmation, stops the queue and retains its unresolved entries in the existing private in-memory draft store; reopening the same exam under the same account/school offers an explicit retry. Pending drafts do not survive a browser refresh, tab closure or intentional sign-out, and are never written to local/session storage. The normal unsaved-changes guard warns before page navigation/unload. Queued writes are bound to the original user and school before sending, including authentication-refresh retries, so switching context cannot send old marks under another account. No authentication credentials are stored in the queue.

For an account with one active school membership, the backend may select that school automatically while the browser's explicit selector is blank. The marks queue verifies `/me`'s owner, resolved school and sole membership, then binds the request to the actual blank transport selector rather than reporting a false context change. Explicit school selection still requires the original school; multiple memberships still require a selection. Actual account/school changes remain blocked by the client guard and backend authorization. This compatibility fix leaves existing pending scores and retry keys in place; use **Retry pending saves** without refreshing a tab holding pending marks.

`GET /api/v1/marks/entry-sheet?exam_id=<uuid>` is the shared source for both workflows. It uses the existing non-bypass API role/RLS, requires `marks.write` and an open examination, checks write/subscription access, and derives the class from the authorized examination. It returns only that class's active enrolled students, permitted configured subjects and existing marks. Subject-test sheets contain only the test's exact subject. Official sheets require the designated Class Teacher (or School Admin); subject teachers cannot obtain them. Parents, Students and Principals cannot use this entry endpoint. It does not accept a client-selected student or class as an authority and returns no account credentials or unrelated profile details. Rosters are capped at 5,000 students with an explicit error above the cap.

CSV uploads use `/marks/bulk`, retaining the existing five-requests-per-minute bulk limit. Keyboard entry uses `/marks/entry`, whose strict shared contract accepts exactly one student/subject row and uses the normal 120-requests-per-minute per-user limit (plus the 600/IP limit). It cannot be used to bypass bulk limits with multi-row bodies. Both routes use the same atomic, audited and idempotent write handler, role checks, enrollment and subject validation, and database exam-lock checks. Single writes audit as `marks.entry`, bulk writes as `marks.bulk`.

Deploy the matching contracts, API and website builds together. This release adds no tables, migrations, accounts or provider credentials and does not modify live marks as part of verification. It relies on the existing class-subject visibility/assessment guards already in the migration chain.

Spreadsheet leading-zero compatibility: numeric subject/student codes such as `0205` can be saved by spreadsheet software as `205`. Import resolves such values only against the already authorized examination sheet, and only when the numeric interpretation identifies one record. It compares digit strings without converting identifiers to floating-point numbers. Numeric roll numbers are checked against the resolved student's own roll, so `003` and `3` remain compatible. Ambiguous numeric codes are rejected rather than assigned to an exact-looking but potentially incorrect student/subject. Alphanumeric codes, class/subject permissions, exam matching, scores and database checks retain their original restrictions; stored codes are never renamed. The import error now distinguishes an unknown student code, unknown subject code and an ambiguous match. Preserve code columns as Text in spreadsheet apps whenever possible.

No tables, examinations, marks or enrollments are copied or migrated. Existing marks retain their IDs and scores. School Admin marks queries include both `class_id` and `exam_id`; the backend intersects these filters through the exam's class. Subject choices reuse the same non-archived teacher-class-subject relationships used by Academics. Individual and bulk writes retain enrollment, exact subject-test subject, maximum-score, exam status, authentication, subscription, role and school checks. Teacher official-exam/Class Teacher restrictions and family/Principal read permissions are unchanged.

For older official marks whose subject mapping has since been removed, the existing selected subject remains on the saved record; this change does not delete or rewrite historical marks. Newly offered subject choices come from the section's configured subjects.

## Verification

Single-school retry fix: 13 focused unit tests and six desktop/mobile browser cases passed. The browser regression uses an administrator with exactly one active school membership and no explicit school selector; it verifies a retained failed entry retries successfully with the original idempotency key and creates exactly one mark. Existing instant-advance and lost-acknowledgement recovery cases also passed. Website production build and type checking passed. Tests use disposable data and simulated external authentication; no live student marks were changed.

Instant-entry update: 17 focused unit checks and 10 desktop/mobile browser cases passed. Deliberately held server replies prove that Enter advances and focuses the next student's field before any acknowledgement; later confirmations preserve the score being typed. Tests cover FIFO ordering, zero scores, repeated edits, failed requests, retries with unchanged keys, close/reopen recovery, prevention of draft resurrection after account/school resets, identity/school binding and authentication-refresh retries. Website production build, type checking, lint, formatting and whitespace checks passed. Temporary browser-test services were closed; the hosted website was not redeployed. Actual database saves remain asynchronous, as the pending/confirmed counters indicate.
